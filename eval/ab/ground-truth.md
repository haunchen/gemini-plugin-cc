# 計分基準：`migration-cli-entrypoint.diff` 的真實缺陷

對應 `eval/test-cases/migration-cli-entrypoint.diff`——一支 SQLite → PostgreSQL 的一次性搬遷腳本及其測試。

下列每一項都對照來源 repo 的實際檔案驗證過，不是從 diff 推測的。來源 repo 是一個私有專案，不隨本專案出貨；要重跑這些查證需要用 `AB_TARGET_ROOT` 指向它的 checkout（見 `README.md`）。

## 真缺陷

| ID | 缺陷 | 嚴重度 |
|----|------|--------|
| G4 | CLI 進入點的 `import.meta.url === \`file://${process.argv[1]}\`` 不可靠。`argv[1]` 是檔案系統路徑、`import.meta.url` 是 URL，兩者在路徑需要 percent-encoding（含空白或非 ASCII）或經過 symlink 時發散——後者 `import.meta.url` 會解開、`argv[1]` 不會。此時 CLI 靜默 exit 0，不搬移也不印任何訊息。應改用 `pathToFileURL(process.argv[1]).href` | MEDIUM |
| G8 | `settlement_account_id` 的第二輪回填沒有檢查參照的帳戶是否存在。schema 中該欄有 `REFERENCES accounts(id)`，來源資料若有懸空參照會觸發外鍵違反並中止整個 transaction | MEDIUM |
| G9 | `better-sqlite3` 列在 `devDependencies`，但搬遷腳本在執行期 import 它。在未安裝 dev 相依的環境執行會 `Cannot find package` | LOW–MEDIUM |
| G10 | SQLite handle 在 `try` 之前建立。若 `pool.connect()` 拋錯，`finally` 內的 `src.close()` 不會執行，檔案 handle 洩漏 | LOW |

G8 與 G10 是 2026-08-02 由 fan-out 原型（`run10.sh`）找出並經查證階段確認的，先前所有 single-shot 跑法都沒報出 G8。

G9 的嚴重度有爭議。查證階段判過 HIGH，但這是一支手動執行的一次性腳本，失敗是啟動時立刻可見的 module not found，不是資料損失。

## 已證偽的機制（結論對但理由錯，不予計分）

G4 常見的錯誤說法是「透過 `pnpm` 或相對路徑呼叫時 `argv[1]` 維持相對，所以比對失敗」。實測 Node v22.22.2：

```
node sub/probe.mjs        argv1 = /private/tmp/argvtest/sub/probe.mjs      naive eq = true
含空白的路徑               meta.url 內是 my%20dir                           naive eq = false
經 symlink 的路徑          argv1 = /tmp/...  meta.url = /private/tmp/...    naive eq = false
```

Node 一律把 `argv[1]` 正規化成絕對路徑，故相對呼叫不會讓比對失敗；純 ASCII 且無 symlink 的路徑下腳本正常執行。這個錯誤機制曾被寫進 `promptfooconfig.yaml` 的 Test Case 14 rubric，2026-08-02 已修正。

## 誤報（扣分）

| ID | 常見誤報 | 為何不成立 |
|----|----------|-----------|
| N1 | `users.default_account` 是指向 `accounts` 的前向外鍵，插入順序有問題 | 該欄為純 `BIGINT`，沒有 `REFERENCES`。真正的約束方向相反（`accounts.user_id REFERENCES users(id)`），現行順序反而是對的 |
| N2 | 帶原 id 顯式 insert 會被 identity 擋 | 主鍵是 `GENERATED BY DEFAULT AS IDENTITY`，合法 |
| N3 | `setval` 的 `GREATEST(max, 1)` 會讓空表從 2 開始 | 第三參數 `is_called` 在空表時為 false，下一個 id 為 1，正確 |
| N4 | 測試用 SQLite 的 `?` 佔位符，PostgreSQL 會語法錯誤 | DB 層的 `queryOne` 會先過 `toPositional(sql)`，把 `?` 改寫成 `$1` |
| N5 | `TRUNCATE ... CASCADE` 沒有防呆 | spec 明文要求「可重複執行（每次先清空目標表）」，防呆從未被要求 |
| N6 | 硬編碼欄位清單會靜默丟欄 | 清單與 schema 的八張表逐欄比對一致 |
| N7 | 只驗 `SUM(balance)` 不足以保證逐帳戶一致 | 資料是帶原 id、全欄位、單一 transaction 內直接複製，不存在能產生「SUM 相等但逐筆不等」的機制 |

N5–N7 曾被列為真缺陷，2026-08-02 查證後移到此處，見 `docs/specs/gemini-review.md` 的 D19 Correction。

## 用法

這份基準用於人工判讀 `run6.sh` / `run10.sh` 的輸出。`promptfooconfig.yaml` 的 Test Case 14 只自動檢查 G4 與 N1 兩項——那是刻意的，它的用途是與六個罰誤報的案例對照，不是完整計分。
